## 设计判断

核心问题是用户需要理解内部操作规则，才能完成普通换装。默认屏幕同时展示文件系统、预览镜和逐槽位替换器；“看一眼”“锁定”“穿上”的边界又依赖悬停、单击、双击。

将产品主界面组织为“衣橱 + 试衣镜”。先让用户找到并看清一套穿搭，再允许调整范围，最后明确穿上。目录管理、存储设置和深度编辑保留入口，但不占据主流程的固定空间。

## 主流程

### 1. 找衣服

- 打开后保持上次目录/列表位置。搜索框默认搜整个衣橱；进入目录后的范围明确显示，可切“仅此文件夹”。清空搜索回到此前浏览位置。
- 主要区域展示穿搭图与名称，次要信息为来源目录。卡片不同时塞入同步按钮、多个动作和状态标记。
- “全部 / 日常 / 正式”等是视图或目录入口，不能复制衣服数据。“收藏”“标签”属于新增元数据，原型示范效果，正式实现排在稳定主流程之后。
- 搜索无结果给“清除搜索条件”；空衣橱给“保存当前穿着 / 导入穿搭”；加载失败提供重试，不能伪装成空衣橱。
- 列表中的 `…` 为管理入口，支持重命名、移动、导出、删除。右键可做快捷入口，不能是手机端唯一入口。只有进入“整理”后才出现多选和批处理。

### 2. 点选后试穿

- 首次打开没有候选时，镜子展示当前穿着，并提示“选择一套穿搭来试穿”。不默认替用户选一套；不显示可执行换装按钮。
- 点卡片创建候选，固定预览。镜子显示“试穿中 · 套装名”“目标：我 / 角色名”；浏览别的衣服不会因路过卡片改掉候选。
- 点另一件替换候选；重复点击同一件不清空、不应用。选择态同时用边框、文字和可访问状态表示。
- “当前穿着 / 试穿效果”切换同一镜子内容，保持相同角度、比例、姿态。切到当前穿着时，主动作应变为“返回试穿”或禁用，避免看到 A 却穿上 B。
- 加载中明确显示“正在生成试穿”，不把旧图当新候选。快速选择 A→B→C 时只允许 C 的渲染结果更新镜子。

### 3. 看清范围，穿上

- 默认范围是“只换服装”，旁边直接写“保留发型、身体与受保护部位”。下方展示实际的替换/新增/移除/保留摘要，不能仅用模式名代替结果。
- 唯一高强调动作“穿上这套”；针对别人时明确写“为 [名字] 换装”。权限从现有适配器读取并在执行前再次检查。
- 未选候选、预览未完成、无实际差异、无权限时不能执行；原因放在按钮附近，不藏在 tooltip。
- 应用中禁用重复执行。成功后显示“已换上 [名称] · 撤销换装”，镜子切到读取回来的真实当前状态；保持列表、搜索与选中项。
- 失败保留候选和规则，显示具体原因并允许调整/重试；不能只记录 console，也不能在结果未知时宣告成功。
- “撤销换装”恢复执行前快照，仍调用权限/资源校验。角色更换、外部穿着变化或快照过期后不盲目回滚，给出明确提示并允许去历史查看。原型的撤销只模拟一次会话内操作。

### 移动端

流程为：衣橱列表 → 点一套 → 全屏试穿详情 → 穿上 / 返回衣橱。

- 顶部始终可返回，底部动作条始终可达；返回后不丢搜索条件、滚动位置和选中项。
- 默认不暴露“列表 / 预览 / 过滤器”三选一控件。换装范围属于试穿详情，“选择部位”在同一详情里展开。
- 列表和详情共用会话状态，视图切换不清空搜索。Escape 先收起当前局部弹层/详情，再关闭衣橱，避免一键丢失上下文。
- 布局按衣橱容器实际宽度转换，不能只看游戏 viewport；桌面悬浮窗缩窄也应进入紧凑布局。

## 换装范围的明确语义

换装范围与执行策略分开。不能把所有模式统称为“筛选”，否则会和找衣服的搜索筛选混淆。

| 用户文案 | 默认处理 | 未包含的部位 |
| --- | --- | --- |
| 只换服装（默认） | 替换套装提供的服装/普通配饰槽位；发型、身体、物品限制和受保护部位保持当前 | 服装槽位默认保留；摘要明确写“仅替换这套包含的服装” |
| 整套外观 | 对允许修改的服装/发型/外观槽位使用候选；仍遵守游戏权限与受保护部位约束 | 服装等可清空槽位缺失时移除；不可清空的身体必要部位保留 |
| 选择部位 | 每个部位明确“使用这套 / 保持当前 / 移除” | 未选择的部位保持当前；无来源物品时禁用“使用这套” |
| 只补空位（高级） | 仅向空的允许槽位添加候选部件 | 保持当前，不移除 |

- “只换服装”不能直接对全 bundle 调用 merge-replace：需限定服装范围，之后与当前非服装部位合并。
- 分组基于 `filterGroupConfig.js` 和资产实际属性。BodyCosplay、隐藏身体、mod 扩展槽位、未知槽位不能凭名字猜测可清空，默认保留并在详情说明。
- 所有范围都原样保留范围外的完整物品，包括 Color、Property、Craft 等数据。整套外观也只移除范围内可清空的槽位；Item 等范围外槽位保持。解析器须依据实时资产组的可清空属性保护必要身体部位，属性未知时保留，不能假设现有适配器已经检查了所有缺失身体槽。
- UI 不提供绕过游戏锁定或权限的能力。已有 `ExternalAdapter.validateOutfitBundleForCharacter` 可用于预检，执行时仍须重验。
- 从候选 A 换到 B：保留用户指定的“保护发型/身体”等偏好；清除仅属于 A 的部件引用并重新计算，不能把 A 的移除规则悄悄套到 B。
- 全部取消选择后明确显示“没有部位需要更换”；零变化不能仍显示成功。
- 原型仅用有限示例槽位演示以上区别，真实 BC 分组映射、锁定、权限、资源缺失和身体必要部位规则需在接入阶段实现与测试。

## 桌面结构与视觉语言

默认两栏：衣橱约 60%，试衣镜约 40%；高级选项不常驻第三栏。常用窗口宽度约 1080–1200px，兼容更小的悬浮窗，保持原本可移动的工具属性，不强制遮住整个游戏。

- 顶部：品牌、目标角色、低强调的保存/数据入口、关闭。只有确有多个可选角色时展示选择器，否则文字显示目标即可。
- 衣橱：搜索 → 目录/视图入口 → 穿搭网格。目录管理使用次级导航，不用庞大的常驻侧边栏挤压衣物。
- 试衣镜：候选身份和状态 → 当前/试穿对照 → 人物 → 换装范围与变化摘要 → 执行动作。
- 米灰/暖灰为背景，干净不透明面板，灰紫为品牌色。主按钮使用高对比深紫；选中卡片用低饱和底色和明显边界。成功、警告同时带文字，不能只靠颜色。
- 4/8px 间距系统；正文约 14px，辅助文字 12px，标题 18–22px。触屏关键命中区域至少 44px。缩略图保持人物比例，使用 contain，不裁掉鞋子、头部和配饰。
- 统一线性图标。避免目前 emoji、字符图标、不同粗细按钮混用；状态文案直说“试穿中”“已穿上”，不向用户暴露 store、bundle、slot 等术语。
- 兼容深浅主题、键盘焦点、较大字号、减少动画偏好。必要内容与管理入口不依赖 hover。

## 状态与 React 落地

生产实现继续使用 React + Mantine + Zustand、现有 Shadow DOM 和角色渲染器。原型的原生 CSS 只负责表达视觉，不引入第二套生产组件库。

建议会话模型：

```ts
type TryOnSession = {
  targetKey: string;
  selectedOutfitId: string | null;
  sourceName: string;
  sourcePath: string[];
  sourceRevision: string;
  mode: 'clothes' | 'appearance' | 'custom' | 'fill-empty';
  overrides: Record<string, 'original' | 'incoming' | 'empty'>;
  compareView: 'current' | 'candidate';
  phase: 'idle' | 'rendering' | 'ready' | 'applying' | 'applied' | 'error';
  requestId: number;
};
```

关键约束：

1. 文件身份与预览 payload 分开。重命名、移动、同名文件不能错指；稳定 ID 应先与 main 的身份/迁移修复整合，过渡期使用来源路径加名称并处理失效。
2. `currentAppearance + candidate + scope + overrides → resolvedBundle + diff + structuralValidation` 由纯函数生成；镜子、变化摘要和提交使用同一份已解析结果。运行时权限与资源校验由适配器预检并在执行前重验，不复制到纯函数中。当前执行路径才调用 `applyPlayerCraftingToBundle`（`fileSystemStore.js:1208–1211`），而 craft 补全可能改变颜色及 `Property.TypeRecord`（`craft-resolver.js:220–241,292–294`）。接入时需把候选的 craft 解析纳入预览，明确保留/受保护部件不能被补全改写；提交不得再静默改变所见结果，撤销也不能二次补全快照。
3. 预览基准带目标角色与外观 revision。提交前当前外观若有变化，重新解析并显示差异；不能让所见与执行使用不同基准。切换目标时保留候选身份，但立即失效旧图、解析、差异和提交状态；清除属于旧目标的部件引用，基于新目标重新解析、校验并渲染，完成前不能应用。
4. 渲染缓存键包含角色、候选 revision、规则和外观 revision；每次选择递增 requestId，丢弃过期响应。
5. `query / searchScope / collection / scroll / focusedOutfitId` 放在会话或 workbench store，不能留在会被手机详情卸载的列表组件里。
6. 提交成功后读取游戏状态再更新 current，不用乐观宣告完整成功；若和预计结果不同，显示实际情况。撤销快照按角色隔离。
7. 历史仍作为独立浏览来源，但复用同一个试穿→提交流程，避免直接应用、预览应用、右键应用三条路径规则不同。

| 建议组件/模块 | 复用/替换位置 | 职责 |
| --- | --- | --- |
| `WardrobeBrowser` | `FileManager` | 搜索、目录、列表，保留上下文 |
| `OutfitCard` | `FileItem` | 选择和可访问管理入口，不直接改变角色 |
| `TryOnPanel` | `SidePreview` | 来源、状态、对照、渲染与动作 |
| `ApplyScope` | `FilterManager` 默认区 | 用户任务语言的范围选项 |
| `PartOverrides` | `FilterManager` 明细区 | 原来的逐部位能力，按需展开 |
| `resolveTryOn` | store 中解析逻辑提取 | 统一结果、差异、预检输入 |
| `useTryOnSession` | store/session | 选择、异步状态、提交、单步撤销 |

## 后续功能的流程

**保存**：镜子旁“保存试穿方案” → 名称/文件夹小弹窗 → 保存即留在当前位置。另提供“保存当前穿着”，避免保存对象不一致。不同步状态与覆盖同名结果需明确展示。

**局部混搭**：选穿搭 → 选择部位 → 只使用鞋子/上衣等 → 预览组合 → 穿上或保存。默认只列当前和候选涉及的部位，再提供“全部部位”。顶部常显“已调整 N 处 / 重置”。

**调色**：后续从具体部位进入调色抽屉，修改只影响试穿草稿；关闭抽屉回到同一预览。无需先学会完整 Studio 的层/堆栈模型。当前 React 没有此 UI，本次不假设已接通。

**导入/导出/同步**：衣橱顶部“导入”独立于保存；导入完成给新增数量和“查看导入穿搭”。同步状态集中于数据入口，需要时显示失败/本地保存信息；卡片默认不把云开关做成视觉主角。既有数据合并与修复另行验证，不在 UI 设计中重写。

## 实施顺序与验收

### 第一阶段：先让换装可靠可理解

- 稳定候选选择、名称与来源、去掉 hover/双击的隐含换装语义。
- 同时统一卡片、镜子与历史的所有执行入口；历史暂时可以只提供“试穿此记录”，然后进入同一提交流程，避免保留绕过规则的直接应用。
- 手机往返保存搜索和滚动，点卡片进入详情。
- 默认换装范围说明、准确 diff、零变化与无选择禁用、成功/失败反馈。
- 接入并校验单步撤销。先完成 main 与 React 的持久化差异评估，再发布。

### 第二阶段：替换外壳与浏览层级

- 两栏、主题 tokens、卡片密度、镜子动作区、容器响应式布局。
- 默认全衣橱搜索、路径展示、明确范围、真实排序数据。尚无使用时间数据时不能把“插入顺序反转”标作“最近穿过”。
- 高级逐部位规则折叠，恢复入口始终可见。

### 第三阶段：增强能力

- 收藏/标签元数据与迁移、保存试穿方案、历史浏览体验，再迁移调色等编辑能力。

验收用实际任务而不是仅看截图：

| 场景 | 必须满足 |
| --- | --- |
| 未选择穿搭 | 显示当前穿着；无可误触的换装操作 |
| 点 A，移到按钮，重复点 A | 候选始终为 A；不会解锁、清空或自动穿上 |
| 快速 A→B→C | C 的名称、图像、diff 与提交结果一致 |
| 已有衣服时默认换装 | 替换候选包含的服装；发型/身体保持；摘要正确 |
| 只选鞋子 | 只有鞋槽发生改变，其他全部保持 |
| 整套外观含移除 | 显示移除明细；必要身体槽和受保护槽不被清空 |
| 切回“当前穿着” | 不会在显示当前时误执行候选 |
| 搜索后手机试穿再返回 | 搜索词、结果、滚动和焦点均恢复 |
| 无搜索结果/无差异 | 明确解释并给下一步，不展示假成功 |
| 换装成功后撤销 | 恢复执行前状态；目标改变或外部变化时重新校验 |
| 渲染失败/权限变化/缺失资源 | 不提交旧预览；候选保留；说明失败原因 |
| 320px、宽桌面、小悬浮窗、深浅主题 | 不横向溢出；关键控件可达；无只靠hover入口 |

这些是后续生产验收标准，不代表本次示例原型已通过真实游戏集成测试。
