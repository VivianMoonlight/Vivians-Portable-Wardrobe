# 多端衣橱同步：可选 Cloudflare 与 BC 模式

衣橱以本机 IndexedDB 为编辑与恢复基础，同一时间只选择一种主要云同步方式。默认的 BC 模式使用 `Player.ExtensionSettings`；可选的 Cloudflare 模式使用 Pages Functions + D1。开启 Cloudflare 后不再向 BC 上传衣橱内容；关闭后从当前本机衣橱恢复 BC 同步。Cloudflare 故障时不会自动回退到 BC，以免旧 BC 副本覆盖新修改。两种云端副本不会自动保持一致。

生产构建已在 `.env.production` 配置 Cloudflare 服务地址，服务及数据页面位于 [vpw-cloud-sync.pages.dev](https://vpw-cloud-sync.pages.dev/)；自建构建仍需配置自己的地址。下文 BC 的 v4 正文与设备标记是独立的目标协议，须区分旧版 schema 3 行为；协议是否已在发布包生效，以构建和真机验收为准。实现入口见 [`WardrobeRepository.js`](../src/services/WardrobeRepository.js)、[`cloudflare-wardrobe-client.js`](../src/services/cloudflare-wardrobe-client.js)、[`cloudflare-wardrobe-sync.js`](../src/services/cloudflare-wardrobe-sync.js)、[`wardrobe-sync-marker.js`](../src/services/wardrobe-sync-marker.js) 和 [`extension-quota.js`](../src/services/extension-quota.js)。部署步骤与 API 契约见 [Cloudflare 服务说明](../cloudflare/README.md)。

## Cloudflare 模式：修订号与条件写入

Pages 托管只读的数据查看与 JSON 导出页；持久化写入由 Pages Function 通过 D1 完成，不能把静态 Pages 当作数据库。服务按恢复密钥的 SHA-256 摘要区分衣柜，每把密钥在 D1 只有一条当前记录，不保留服务端历史。`GET /api/wardrobe` 返回当前索引与修订号；`PUT` 带 `expectedRevision`。创建使用原子插入，更新使用 `WHERE revision = ?` 的条件写入：两个设备从同一版本提交，只有一个能成功，另一个收到 HTTP 409 和最新版本。客户端将本机已核对基线、待上传修改与新版本比较，可证明独立的修改自动合并；同一内容的不可避免冲突交给用户选择，不在服务器保存多份冲突正文。请求超时不能证明写入失败；后续重试先重新读取修订号，再判断是否需要提交。Cloudflare 返回成功的 HTTP 响应与修订号；BC 模式则没有逐次写入回执。

在 **设置 → 同步方式** 中开启 Cloudflare 前，脚本必须在打包时配置 `VITE_CLOUDFLARE_SYNC_URL`；当前生产构建已配置。界面没有任意服务地址输入框；未配置地址的自建构建不能新开启 Cloudflare。开关状态与恢复密钥先按 BC 账号保存在本机 IndexedDB。首次开启生成 32 字节随机恢复密钥；也可在关闭 Cloudflare 时导入已有密钥，再开启并合并该密钥对应的云衣橱。导入另一把密钥是**切换到另一份云衣橱**，不是撤销旧密钥：旧密钥仍可访问原 D1 记录，该记录不会自动删除。另一把格式正确的密钥可能指向空衣橱，不能把空结果当作原密钥的数据已被删除。更换密钥或切换模式前应导出当前 JSON 备份。关闭 Cloudflare 不会删除 D1 中的旧衣橱或旧密钥，也不保证当前衣橱能装入 BC 的 180 kB 预算；超限时本机数据仍保留，BC 上传暂停。

恢复密钥可在设置中显示、复制或下载；应在插件外妥善备份。插件还会尝试把明文密钥写入 `ExtensionSettings.VPWCloudKey`，供其他 BC 设备取得；BC 对这一提交不逐次回执，界面的“已提交”不是服务器确认。若未取得密钥，另一设备必须手动导入。持有密钥的人可读取和修改对应衣橱；密钥丢失且本机与 BC 中均无副本时，服务无法找回。数据查看页只在当前页面内存中使用密钥，不把它放进链接或网页存储。D1 保存密钥摘要，但衣橱正文**未端到端加密**，Cloudflare 服务运营者仍能读取衣物内容；能读取 BC 扩展设置中明文密钥的一方也可能访问这份云衣橱。传输使用 HTTPS，BC 站点发起的请求由 Function 的 CORS 白名单处理；CORS 不是身份认证。

同一 BC 账号的其他设备若继续向 BC 同步，BC 旧副本与 Cloudflare 衣橱会分叉。清理旧 `VPWardrobe` 正文和设备标记前，必须取得新鲜 BC 登录快照，并与开启 Cloudflare 时的已知基线比较；若旧副本已变化、来源无法确认或没有新鲜快照，应暂停清理并让用户审阅，不能把这些修改当作可丢弃的旧数据。确认 Cloudflare 已保存且 BC 旧副本未变后，才可提交清理，同时保留 `VPWCloudKey`。这次 BC 清理仍没有逐次回执，只有后续完整登录回读才可核对；检查后的迟到 BC 写入也不能靠客户端快照比较阻止，因此其他设备仍须切换或停用 BC 同步。在核对完成前，旧副本可能继续占用 BC 共享预算。

Cloudflare 模式的每份云衣橱 JSON 主动限制为 **1,800,000 字节**，与 BC 模式的 **180000 字节**预算是两种独立限制。当前免费服务另设 100 把密钥、每个 IP 每 UTC 日创建 2 把、每把密钥每 UTC 日写入 500 次的保护上限；达到限制时保留本机修改并提示重试或处理容量。D1 和 Pages Functions 还有 Cloudflare 平台限制，参见 [D1 容量与行大小](https://developers.cloudflare.com/d1/platform/limits/)、[D1 用量](https://developers.cloudflare.com/d1/platform/pricing/)及 [Pages Functions 用量](https://developers.cloudflare.com/pages/functions/pricing/)。

## BC 模式：单份正文与设备标记

BC 模式只使用 `Player.ExtensionSettings` 同步衣橱。云端的 `VPWardrobe` 是**唯一一份压缩衣橱正文**；每个安装环境另有一个长度有固定上界的标记键，只记录版本和序号，不存衣服内容、衣物 ID 或操作历史。冲突候选、已核对基线和待上传修改留在各设备本机。此模式按空间优先取舍：发现正文遗漏修改时，等待原设备恢复，或由用户明确选择放弃缺失修改。以下协议、容量和验证章节只讨论 BC 模式。

## BC 接口边界

- 旧版把压缩的 schema 3 索引写入 `ExtensionSettings.VPWardrobe`。本机先保存；`ServerPlayerExtensionSettingsSync('VPWardrobe')` 只发送整份云投影。`submitted` 仅表示已调用发送接口，界面默认视为同步成功；下次完整登录收到的新鲜 `LoginResponse` 用于检查差异或冲突，并非逐次写入回执。首次打开时的 `Player.ExtensionSettings` 缓存不能充当云端确认。
- [BC 客户端同步函数](https://gitgud.io/BondageProjects/Bondage-College/-/blob/02a7130050fcce7c96fcebf252b39dbbc1b0f1ed/BondageClub/Scripts/Server.js#L643-654)每次只构造一个设置字段。目标协议需以一次 `AccountUpdate` 发送 `ExtensionSettings.VPWardrobe` 和本设备的 `ExtensionSettings.VPW4_M_<deviceId>` 两个字段。[所核对版本的 BC 服务端](https://github.com/Ben987/Bondage-Club-Server/blob/9cfaaeffab8b417df9db7fcb0d1e3b9092b6c922/app.js#L698-L813)以一次 MongoDB `$set` 写入收到的更新，但没有条件写入（CAS）或逐次成功回执。按不同点号路径写入的假设，以及这两个字段在实际账号上的同次持久化，必须先做真机验证。
- [服务端配置](https://github.com/Ben987/Bondage-Club-Server/blob/9cfaaeffab8b417df9db7fcb0d1e3b9092b6c922/app.js#L37)的 `maxHttpBufferSize: 180000` 是 Socket.IO **单包**上限。产品另按用户要求将**整个 `Player.ExtensionSettings` 的 UTF-8 JSON**控制在 180000 字节内；这是 VPW 的保守共享预算，并非已证明 BC 数据库另有相同的总存储上限。拟发送的 `AccountUpdate` 单包也须单独过关。

## 目标数据布局

每个 BC 账号、每个浏览器安装环境生成随机且稳定的 128 位 `deviceId`，仅在本机持久化。同源标签页共用该 ID；换设备或清除本机存储会产生新 ID。键名只使用安全字符，例如 `VPW4_M_` 加 32 位十六进制 ID，不含玩家、设备名称或个人信息。

| 位置 | 内容 | 用途 |
| --- | --- | --- |
| `ExtensionSettings.VPWardrobe` | 一份 LZ Base64 压缩的 `{protocol:'VPW4',index,a}`；`index` 是共享衣橱投影，`a` 是已处理的各设备序号 | 显示与同步共享衣服、标签、墓碑和同步范围 |
| `ExtensionSettings.VPW4_M_<deviceId>` | JSON 字符串 `{"v":1,"s":序号}`，每次写入仍为固定最大长度 | 发现正文被旧快照覆盖；不保存丢失的内容或删除、撤回 ID |
| 本机账号存储 | 完整索引、已核对云端基线、待上传操作和冲突候选 | 离线工作、三方合并和恢复；不算作 BC 云端副本 |

标记格式如下。`v` 是标记格式版本，不是衣橱协议版本；`s` 为非负安全整数。该 JSON 字符串最多 28 个 ASCII 字节，编辑、删除多少件衣服都不增长。衣物删除的墓碑在唯一正文及本机索引内；旧 ID 不再复用，恢复须创建新 ID。

```json
{"v":1,"s":17}
```

正文中的 `a[deviceId]` 表示已处理该设备的最大连续序号：正常情况是修改已合入，用户明确放弃缺失修改后也会把相应序号记为已处理，二者不能混作“修改已保存”的证明。例如 A 标记为 17，而正文仅处理到 A 的 16，就有一个**缺口**：不能把正文当作完整云端状态，也不能宣称 A 的第 17 次修改已核对。标记不含衣物 ID，更不能凭它推断丢失的是删除、撤回、改名还是新增。因此只要有**无法从本机完整待提交内容恢复的缺口**，整份云同步衣橱都进入隔离：不展示或合并其中任何共享衣物及标签，也不自动上传；仅本机私有衣物仍可使用。原设备可用完整本机数据修复，或由用户明确放弃该设备缺失的序号后重新合并。放弃可能使未知删除或撤回失效，必须明确告知。撤回同步也不承诺从其他设备本机即时物理抹除旧字节。

同一设备明确重新开启某件衣服的同步时，新的发布与本设备递增的标记必须同次提交。若之后旧正文覆盖了这次发布，序号缺口须使客户端隔离并处理，不能把旧内容视为已核对。另一设备同时撤回、重新发布同一 ID 属于内容冲突，交给用户审阅；不得简单用墙上时钟定胜负。

## 本机修改、合并与提交

1. 修改先持久化到本机索引与待上传队列，再更新界面。存下最近一次经新鲜 `LoginResponse` 核对的基线；离线和容量不足时仍可浏览、编辑、导出。多个同源标签页必须串行化本机写入和该设备 `seq` 的分配，否则它们会相互覆盖同一个标记键；无法取得可靠锁时暂停其中一方上传。
2. 下次完整登录时读取**同一个新鲜快照**中的 `VPWardrobe` 与全部 `VPW4_M_` 键。普通断线自动重连不一定重新加载 `ExtensionSettings`，不能把旧缓存当作新鲜快照。先验证账号、版本、编码和标记格式，再比较每个标记的 `s` 与正文 `a[deviceId]`。未知版本或损坏数据不能当空衣橱。任一未知缺口都隔离整份云同步衣橱并阻止自动上传；本设备若持有完整待提交版本，可先从本机恢复再核对。正文领先于相应标记、标记缺失或序号倒退也需要保守处理，不能推断已成功同步。
3. 以已核对基线、本机待上传修改和新鲜云端正文进行三方比较。不同衣服或同一衣服不同字段且可证明独立的修改可以自动合并；同一字段、外观或同步范围的并发冲突展示本机候选与云端值，由用户选择或手动合并。候选只存在本机，不自动复制进 `ExtensionSettings`。删除优先于对旧 ID 的迟到编辑；明确恢复用新 ID。标签仍保持全局唯一名称和多标签关联，不能借冲突处理悄悄创建同名标签。
4. 准备提交时，先核算完整设置和实际发送包的字节数。用**同一个** `AccountUpdate` 更新正文和本设备标记；绝不能先单独写标记、再单独写正文。接口没有逐次成功回执，提交调用成功后界面默认视为同步成功，本机继续保留后续冲突比对记录；下次完整登录的新鲜 `LoginResponse` 若同时包含预期正文、该设备序号且没有其他标记缺口，可显示“已与云端核对”。这不是每次提交都要等待的确认。若服务器在发送前后被另一设备写入，客户端没有 CAS 可阻止竞态，只能检测可检测的回退并保留本机恢复依据。
5. 多端冲突未解决、来源不明、容量超限或解码失败时停止自动上传，保留本机修改并提供导出。其他设备在尚未读到冲突标记前仍可能发送旧正文；该限制必须反映在状态文案中。

一个可复现的交错：A、B 都从 S0 出发；A 改名 X，上传正文 A1 与标记 A:1；B 从旧 S0 新增 Y，晚上传正文 B1 与标记 B:1。云端仍只有一份正文 B1，但 A:1 标记留在另一键，而 B1 的 `a[A]` 为 0。新版客户端因此隔离 B1 的**所有共享内容**；A 本机还在时可提供改名候选。**若 A 的本机数据和备份均丢失，云端标记只能证明有缺口，无法还原新名字。**用户可明确放弃 A:1，但须接受那次修改永久丢失的可能。

## 容量与界面状态

每次估算将拟写入的 `VPWardrobe` 和本设备标记替换进当前 `Player.ExtensionSettings`，计算整个对象序列化后的 UTF-8 字节数，并另算 `AccountUpdate` 实际 Socket.IO 包。界面显示衣橱正文与全部设备标记、其他扩展、总量和剩余量。每个标记的值最多 28 字节；含键名、引号和分隔符最多约占 77 字节。目标最多累计登记 16 个设备键（含历史设备，不是同时在线 16 台）；第 17 个新设备只保留本机修改和导出能力，不允许云写入。设备标记总数有界，但正文中的衣物墓碑及设备序号映射仍计入容量；尤其墓碑会随删除历史增长，不能宣称全部同步元数据恒定。80% 可作为预警，不另称服务器上限。任一检查超过 180000 字节就停止上传，不截断索引、不自动清理墓碑、不丢弃本机待上传修改。

状态至少区分“本机已保存”“已提交（默认成功）”“已与云端核对”“云端内容已隔离”“需要处理冲突”“空间不足，未上传”“设备数已满，仅本机保存”。“重试上传”不得暗示已经刷新到最新服务器值。BC 没有可依赖的条件删除或旧端写入栅栏，遗失设备的标记不能自动修剪或复用；即使用户放弃一次缺口，也不应删除其标记键，因为旧设备可能长期离线。空间吃紧时先提示导出、转为仅本机保存或让用户明确清理内容。

## 从 schema 3 迁移

首次升级先备份现有本机索引与原始 `VPWardrobe` 压缩值，保留可导出的恢复材料。只有在读取并校验新鲜云端 schema 3 快照、且不存在未解释的 v4 标记时，才把稳定衣物和标签 ID 转入 v4 正文并初始化本设备标记与 `a`。本机私有衣服继续只留本机；云端缺少衣服不等于删除。迁移提交仍用正文与标记的同包写入；提交后默认视为成功，下次完整登录回读时再检查差异和冲突。

旧版客户端仍可能把 `VPWardrobe` 写回 schema 3。BC 没有服务端旧版写入栅栏；新版再次看到 v3 正文与 v4 标记并存时，应暂停自动迁移或覆盖，使用本机备份与用户处理，不能把旧正文当成新的权威状态。发布说明需提示同一账号的所有设备升级；仅更换前端版本不能保证旧端不再写入。

## 验证门槛与不能承诺的事

先用真实 BC 测试账号确认：动态 `VPW4_M_` 键写入后能在下一次 `LoginResponse` 返回；正文和标记的两个点号路径在一次更新中一同持久化；更新一个标记不覆盖其他设备标记；实际单包与整个设置的字节数符合预算。源码支持该设计推断，但模拟测试不能替代这些检查。

再用可控两端模拟器固定交错顺序，覆盖新增 X/Y、删除 X 与编辑 Y、改名与改标签、同一外观冲突、撤回与旧端重发、撤回后明确重启同步、缺口时整份云衣橱隔离、原设备修复与明确放弃、两个标签页共用 ID、第 17 个设备、离线重试、丢包、损坏编码、超容量和旧版 v3 回写。逐例检查两台本机、唯一云端正文、全部标记、待上传队列、冲突候选和 UI 状态。

此协议没有 CAS、逐次回执或独立后端，不承诺任意并发操作都自动无损。它以长度有界的标记发现部分“已发送但正文被覆盖”的情况，并隔离有疑问的整份共享衣橱；若唯一持有修改内容的设备及本机备份永久丢失，标记无法还原内容。长期离线旧端、最多 16 个历史设备、不能安全自动删键和无法即时物理擦除旧副本仍是设计边界。
