# 多端衣橱同步：现状、冲突与演进方案

这份设计针对同一账号在多台设备上分别新增、删除、改名、改标签和编辑衣服的情况。目标是让用户知道**哪份数据只在本机、哪份已提交、哪份经过云端核对**，并在冲突时保住可恢复的版本。当前 BC 接口只给 VPW 一个 `Player.ExtensionSettings.VPWardrobe` 值；在没有服务端条件写入的前提下，不能承诺任意并发操作都无损。

## 已核对的现有实现

以下来自 [`WardrobeRepository.js`](../src/services/WardrobeRepository.js)、[`wardrobe-index.js`](../src/services/wardrobe-index.js) 和 [`extension-quota.js`](../src/services/extension-quota.js)；操作说明见[索引与云同步](INDEXED_WARDROBE_SYNC.md)。

- 每个账号在 `localStorage` 有一份压缩的 schema 3 索引和待上传状态。服装、标签分别有稳定 ID；内容以整条记录的 `[逻辑计数器, 副本 ID]` 选择胜者。`cloudState[id]` 有独立修订；删除使用不自动过期的墓碑。同名标签合并展示并保留 ID 别名。
- 云端是索引的**投影**：关闭同步的服装内容不上传，但开关元数据、标签和墓碑仍上传。云端缺少服装不等于删除。本机甲、本机乙和云端内容因此可以合理地不完全相同。
- 浏览与搜索读取当前设备的本机索引；另一台设备的改动要等可用的云端快照被接收、合并后才会出现。现有“重试上传”不会主动从服务器读取新快照。
- 操作先写本机，再经 `ServerPlayerExtensionSettingsSync('VPWardrobe')` 提交整份压缩投影。代码将 `submitted` 定义为已调用发送接口，将 `verified` 定义为本会话收到的新鲜云端快照与投影相符；发送接口本身没有逐次确认或比较并交换（CAS）。登录的 `LoginResponse` 可提供新鲜快照。首次 `open()` 只把 `Player.ExtensionSettings` 当作暂存缓存；缓存与本机投影相同时不会仅因打开或点击重试而重新上传，也不会标为已核对。本会话有实际编辑时仍可尝试提交，因此并发覆盖风险仍在。
- 提交前合并同源其他标签页存储；这不是跨标签页原子事务。离线、编码错误、容量超限时，本机保存的数据和待处理状态仍是恢复依据。

### 多端时序与结果

| 两台设备从同一旧快照开始 | 当前可发生的情况 | 目标处理方式 |
| --- | --- | --- |
| 甲新增衣服 X，乙新增 Y | 如果双方最终重新读到对方仍持有的索引，两个 ID 可合并；乙从旧快照晚上传时，服务器暂时只剩 Y。甲永不回来则 X 无法由服务器恢复。 | 保留两边操作；条件写入失败时读新版本、合并、重试。 |
| 甲删除 X，乙只编辑 Y | 甲本机有 X 的墓碑；乙的旧投影没有它。乙晚上传会覆盖云端墓碑，旧 X 可能在其他设备重新出现。 | 删除优先；服务器拒绝基于旧版本的覆盖，重试时带上墓碑。 |
| 甲将 X 改名，乙只编辑 Y | 乙晚上传可暂时把云端 X 的旧名字带回；若甲不再上线，改名无法从云端找回。 | 按实体/字段重放操作；有因果关系的旧名字不能覆盖新名字。 |
| 两端同时改同一件衣服不同字段 | 目前按整条服装记录选一个胜者，即使一边只改名、一边只改标签，也可能丢掉另一边的字段。 | 字段级合并；无法安全合并的外观版本保留冲突副本，交给用户选择。 |
| 两端同时给同一标签改成不同名字 | 同一标签 ID 目前按整条标签记录选一个名字；被选掉的名字不会自动留作冲突版本。两端新增同名标签时会保留 ID 别名并合并展示。 | 同一 ID 的并发改名保留候选值；全局同名仍只显示一个标签，并保留旧 ID 的引用。 |
| 甲关闭 X 的云同步，乙持有旧 X | 双方再次交换状态时，单独修订的开关可阻止旧内容重新开启；但乙从旧快照晚上传仍能抹掉服务器上的关闭状态并重新发布 X。 | 关闭同步视作隐私边界；服务器版本检查必须阻止旧客户端重发。 |
| 甲重新开启共享 X，乙有未共享的本机改动 | 当前合并会把乙的私有修改另存为仅本机副本，原 ID 使用甲明确发布的内容；双设备与同源双标签页回归已覆盖。乙若在接收甲的新状态前先上传旧快照，单字段竞态仍可能发生。 | 乙的私有改动留在仅本机的新 ID；只有乙明确选择“发布到云端”才可共享。 |

反例很短：云端为 S0；甲读 S0 后上传含 X 的 S1；乙也读过 S0，随后上传只含 Y 的 S2。服务器只保留最后的 `VPWardrobe=S2`，没有 S1 的版本或操作日志。乙仅凭 S0 和 S2 无法推断 X 曾存在；甲退出或清理浏览器后也没有可恢复来源。**发送前再读一次、发送后再读一次、给本机修订编号或延长重试时间，都不能消除两次读写之间的竞态。**这也解释了为何“已提交”不能写成“已安全同步”。

## 第一阶段：在现有 BC 接口上收紧安全边界

这些改动可以提升本机安全和透明度，但仍不能把单字段整块覆盖变成无损的多端事务。

1. **只信明确来源的新鲜云端快照。**首次打开时读取 `Player.ExtensionSettings` 只能作缓存参考，不能凭它验证成功。当前已阻止“旧缓存与本机相同”时的无意义自动重传；登录、重连取得带账号身份的 `LoginResponse` 后才会核对。没有该快照时保留本机待同步队列，显示“等待云端核对”。本会话新编辑仍会尝试上传以保留正常使用，因此这一步不能阻止另一设备在读写间抢先写入。
2. **本机写入先行，冲突内容可恢复。**持久化原始操作/待上传状态与最近一次已核对的云投影；同一服装的并发外观修改保留失败方为冲突副本或恢复记录，不静默丢弃。任何解码失败或不认识的版本都应暂停自动上传，不能当作空衣橱。
3. **把私有内容与共享 ID 的发布分开。**当前已将另一设备重新开启同步后出现的本机私有修改保留为独立的仅本机副本，并在卡牌/列表标明；用户可再明确开启该副本的云同步。这个本机修复不能阻止尚未收到新状态的旧设备覆盖整个云字段。删除本机副本时，当前墓碑可能上传其来源 ID/修订元数据，但不会上传衣物名称或内容；彻底只保留本机的删除元数据需要后续结构调整。
4. **容量超限只阻止上传。**拟提交内容要按完整 `Player.ExtensionSettings` 的 UTF-8 JSON 字节数计算，同时核算这次 `AccountUpdate` 包。界面分别显示 VPW 用量、其他扩展用量、总量和剩余量；超过共享的 180000 字节策略时保留本机修改与导出能力，不自动删墓碑或旧记录。80% 提示是预警，不是另一个服务端配额。[BC 服务端配置](https://github.com/Ben987/Bondage-Club-Server/blob/9cfaaeffab8b417df9db7fcb0d1e3b9092b6c922/app.js#L37) 的 `maxHttpBufferSize: 180000` 是 Socket.IO 单包上限，不是给 VPW 独占的额度。
5. **在界面区分范围与状态。**每件衣服标识“仅此设备”或“参与云同步”；同步状态使用“本机已保存 / 等待核对 / 云端已核对 / 上传受阻”，并给出最后核对时间、容量及可恢复冲突数量。“重试上传”不能表述为“刷新云端”。

## 第二阶段：需要有条件写入的共享存储

要保证两台活跃设备的已接受修改不被另一台旧快照无声覆盖，首选为 VPW 提供**服务端原子的版本校验**。例如读取 `(payload, generation)`，写入时附带原 `generation`；若它已变化，服务器拒绝写入并返回新版本，客户端合并后重试。HTTP [`ETag` / `If-Match`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-Match) 是这种防止“丢失更新”的现成语义；[CouchDB](https://docs.couchdb.org/en/stable/replication/conflicts.html) 用先前修订号拒绝旧写入，也会保留可供处理的冲突版本；[Firestore 事务](https://firebase.google.com/docs/firestore/manage-data/transactions) 会对冲突重试且离线事务失败。这些是设计参照，**不是 BC 现有接口已具备的能力**。

建议的索引 v4 和同步循环如下：

1. 本机为每账号持久化稳定 `deviceId` 和单调操作序号。每次创建、删除、改名、调标签、编辑外观、变更同步范围生成唯一操作 ID，并在 IndexedDB 同一写事务中更新可见索引与待上传队列。浏览器崩溃后可重放；多标签页经同一事务串行化。
2. 共享服装保持稳定 ID，字段或操作带因果上下文。不同字段的非冲突修改可合并；标签关联独立于衣服内容，以“同一关联并发增删时移除优先”为规则，后续明确添加可以重新关联。删除衣服或标签保留墓碑并优先于迟到的旧编辑。并发修改同一名字或同一外观时，保留两个候选值或冲突副本，不靠物理时间悄悄挑一个。
3. 本机私有衣服与共享投影分开储存。发布是一项显式操作，产生可追踪的共享版本；别的设备开启共享不意味着本机未发布的改动自动公开。共享衣服被改成仅本机时，先使服务器确认撤回，再把每台已有的本机副本视为各自私有内容；旧设备必须先重同步才能继续写入。
4. 客户端读取服务器版本、合并远端操作与本机待处理操作，计算投影和容量，再以该版本条件提交。版本冲突则重新读取、重放、合并和限次重试；成功响应携带新版本及摘要后再移出待处理队列。离线只写本机；恢复后走相同流程。禁止把“已发出请求”当成服务器确认。
5. 服务端提供旧设备写入栅栏或最低可接受世代，并有清晰的版本迁移路径：先备份 schema 3，本机升级 v4；旧客户端不得再写旧格式，所有设备在下一次登录时以服务器世代重建共享基线并重放本机操作。**当前 BC 单字段接口没有这道栅栏**，所以不能仅靠客户端换 schema 就声称迁移安全。

如果 BC 无法增加条件写入，一个待验证的替代方案是每设备占用独立云端键，再合并所有键；它需要先证明 BC 对不同键的更新不会互相整块覆盖，还要解决同设备多标签页、遗失设备键、旧版写入和 180000 字节总预算。尤其是关闭同步或删除衣服时，旧设备键里仍可能留有内容，必须逐键撤回并阻止离线旧设备重发；仅把数据分片**不能**保证私有内容下云或删除生效。设备越多，元数据越大，因此它不是默认方案。独立服务可提供真正的事务与容量，但会引入账号授权、托管和数据隐私决策，需另行设计。

墓碑不能因“过了一段时间”就删除：长期离线设备可能仍持有被删实体。将来只有在服务器可阻止旧世代写入、所有仍被允许的设备已确认新检查点，或旧设备强制重新初始化时，才能安全压缩墓碑与操作日志。容量不足时应优先提示导出、选择仅本机保存或由用户清理内容。

## 验证标准

用可控的两端模拟器固定交错顺序，而不只测试单端合并函数：新增 X/Y 后轮流上传；删除 X 与编辑 Y；改名 X 与改标签 X；两个外观版本；关闭同步与旧设备上传；重新开启与另一端私有修改；同名标签并发创建及改名；超容量后本机重启；断网、发送超时、重复提交、响应丢失；两个同源标签页同时写。每例检查两台本机、云端投影、待处理队列、恢复副本和 UI 状态。另用真实 BC 测试账号在两台设备上核对登录快照与服务端容量边界；模拟宿主测试不能证明 BC 的回执、缓存或键更新行为。
